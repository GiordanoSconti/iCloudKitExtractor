Inside MMCS and authorizeGet: a code map

Day 11 lists the wire facts that survived months of restores. This note is the other half of that picture: where those facts live in iCloudKit Extractor. It is a map of the download spine—from CloudKit Lock through MMCS authorizeGet, FileGroups, edge ranged GETs, IKM, Ford, and ChunkInfo—written so a reader can follow the mechanisms in the repository without treating any third-party client as the source of truth.

The language stays descriptive. The anchors are types and paths under src/iCloudKitExtractor. Private Apple surfaces move; the map describes what the tree encodes today.

The spine in one glance

A backup restore that still has live MMCS assets climbs the same ladder every time. CloudKit names the inventory; MMCS delivers the bytes; PCS/CKKS material turns those bytes into files. In code the ladder looks like this: 

CloudKit (mbksync)
  zones → BackupAccount → D:<sha> → S:<uuid>
  → Lock → N: / EN: file lists + asset metadata
       ↓
MMCS
  x-apple-mmcs-auth  →  POST …/{dsid}/authorizeGet
  → FileGroups (host templates + ChunkInfo + trailing refs)
  → GET edge  ?content-byte-range=start-end
       ↓
Crypto open
  contents.protectionInfo → IKM
  → HKDF-SHA256(salt="PCSMMCS2") → Ford keys
  → ChunkDecrypt / VerifyDigest → iTunes-shaped tree

Everything below is that ladder, stage by stage, with the types that own each step.

1. Session binding and content hosts

Before any ranged GET, the session must know which content partition to speak to. Partition and optional per-record content bases become authorizeGet hosts in Services/Download/MmcsContentEndpoints.cs (BuildAuthorizeGetHosts): typically https://{partition}-content.icloud.com, plus a record-level ContentBaseUrl when it is not the generic gateway. The same type also decides when an authorizeGet plan is incomplete—missing chunk URLs, missing edge signatures, or a summed byte-range shorter than the declared size (IsAuthorizeGetIncomplete). Incomplete plans are hard failures; guessing the missing range is how caches get poisoned.

2. The MMCS auth header

Edge authorization is not a bearer token alone. It is the HTTP header x-apple-mmcs-auth, shaped as three whitespace-separated pieces: a 21-byte hex token, a second 21-byte hex token, and a base64url protobuf often recognized by a CAog… prefix and a decoded payload that carries Foreground Restore markers. Construction and extraction live in Protocol/MmcsAuthBuilder.cs.

That builder walks record payloads (including snapshot S: / &S: forms), prefers structured sibling fields when PreAuth encoded them as protobuf, and falls back to ready-made header strings already present on the wire. For per-file authorizeGet entries the discipline that stuck is strict: f1 is the Assets assetSignature verbatim (21 B, usually 0x04‖20B); f2 is the CAog token string; f4 is the companion 21-byte token (often 0x01‖20B). Rebuilding a batch header from the wrong field —for example treating a CloudKit mmcs-auth part0 as f1—produces plans that look authorized and then fail at the edge.

3. authorizeGet: the ubchunk conversation

The request and response MIME type is application/vnd.com.apple.me.ubchunk+protobuf. Parsing, host templates, Ford descriptors, data ChunkInfo classification, and ownership checks on gates all concentrate in Protocol/UbChunkBuilder.cs—the largest protocol surface in the download path. Higher up, Services/Backup/CloudKitAssetService.cs and Services/Download/BackupDownloadService.cs schedule PrivilegedBatch / authorizeGet waves, refresh Anisette when the edge rejects identity, and hand each successful plan downstream as an AuthorizeGetDecryptPlan.

A healthy response is a list of FileGroups. Each group maps to one edge GET host (URL from template fields) and carries nested ChunkInfo: checksum (21 or 45 B), optional chunkEncryptionKey, ciphertext length, pack offset, and trailing file-checksum chunk references that define assembly order. The plan is not “a list of URLs.” It is a contract between signatures, ranges, and later decrypt stages.

4. Edge GET: one object, two personalities

Fetching uses query parameter content-byte-range={start}-{end} against the host chosen by the FileGroup. The same object can expose Ford key material at offset 0 and data ChunkInfo at other ranges. Mixing those roles is the classic silent failure mode: MAC checks fail while every layer reports partial success.

Assembly and caching sit in Services/Download/MmcsChunkStore.cs and Services/Download/MmcsChunkAssemblySession.cs. Sessions are sharded per domain so one FileGroup’s cache cannot contaminate another. On disk, chunks land under .chunks/ (or a temporary CChunkCache), named as lowercase hex of the signature—42 hex characters for a 21-byte data checksum, 90 for a 45-byte Ford gate. Ford plants require size equal to ctLen, a plausible lead byte (typically 0x04), and an IKM that actually opens the blob. Planting Ford without IKM is how a cache becomes a museum of convincing garbage.

5. Opening the plan: FileGroupFillDecrypt and LiveFill

Once host bodies are on disk, Services/Escrow/FileGroupFillDecrypt.cs owns the observational and production decrypt path. The order that survived summer caching wars is deliberate:

  1. authorizeGet → FileGroups already parsed into the plan;
  2. ranged GET bodies available to the assembly session;
  3. Ford SpillOpen for storages whose gates are owned by this plan;
  4. FillChunks only for storages that already hold Ford keys;
  5. data ChunkDecrypt with VerifyDigest / MAC checks.

Ownership matters. A 45-byte gate with lead pattern 0C 0F 01 04 is not a 21-byte data checksum. UbChunkBuilder helpers (IsAuthFordDescriptorChunk, GateOwnsPlan, GateEmbedsFileChecksum, IsAuthDataChunk) decide whether a descriptor belongs to this file’s authorizeGet plan or is leftover material from a sibling group in the same batch. Nested empty-OID gates without a matching CI45 on a referenced host are skipped; treating them as local Ford is another poison vector.

6. IKM and the Ford KDF

Ford does not open on the file-list EncryptionKey. The IKM comes from the owned CloudKit record’s contents.protectionInfo, unwrapped with the zone master (16 or 32 B). That distinction is the single most expensive lesson in the MMCS path: the wrong key produces ciphertext that almost looks right and never verifies.

Derivation, checked against live captures, is: 

HKDF-SHA256(
  ikm  = fileKey,          // from protectionInfo unwrap
  salt = "PCSMMCS2",
  info = "",
  len  = 64                // 0x40
)

Implementation lives primarily in Services/Escrow/FordMmcsDecryptor.cs, with PCS zone unwrap helpers in Services/Escrow/PcsProtectionZone.cs and related share protection types. The Ford blob layout is lead(1) ‖ nonce(16) ‖ body, where body is tag(16) ‖ ciphertext from offset 0x11. Decryption is AES-SIV (RFC 5297) with associated data [nonce, lead]. Per-chunk expansion then uses HKDF info signature-key (0x60 bytes) into k1 / k2 / k3 for MAC, staging, and CTR paths. Classic Auth Ford ciphertext lengths sit in [0x12, 65536]; larger multi-key bags need a host ByteRange at least as long as ctLen, with a sanity cap in the multi-mebibyte range.

7. Data ChunkInfo after Ford

Data chunks carry a 21-byte checksum; MAC verification uses the trailing 20 bytes (VerifyDigest / VerifyDigestWithChunkKey in FordMmcsDecryptor). Staging headers are length 0x28; the little-endian u64 at hdr[0x20] is the wire data length. Lead byte 0x04 at host offset 0 usually marks Ford ciphertext; valid data chunks may start with 0xC4 and other non-0x04 values, including large bodies. Treating every non-0x04 lead as broken Ford was a classifier bug; fixing it unlocked protocol-complete downloads for material that still lived on the edge (see Day 7).

Parallel decrypt workers and in-memory budgets are coordinated through Services/Download/BackupDecryptWorkerQueue.cs so large PrivilegedBatch waves do not turn a correct plan into an OOM.

8. Where the map sits in the tree

For readers jumping into the repository, this is the condensed index:

  • Protocol/MmcsAuthBuilder.cs — x-apple-mmcs-auth build / extract; snapshot-aware.
  • Protocol/UbChunkBuilder.cs — ubchunk protobuf, FileGroups, Ford descriptors vs data ChunkInfo, ownership gates.
  • Services/Download/MmcsContentEndpoints.cs — authorizeGet hosts; incomplete-plan checks.
  • Services/Backup/CloudKitAssetService.cs / Services/Download/BackupDownloadService.cs — batching, Anisette refresh, download orchestration, Lock preparation upstream of MMCS.
  • Services/Download/MmcsChunkStore.cs / MmcsChunkAssemblySession.cs — edge bodies, .chunks/ cache, per-domain isolation.
  • Services/Escrow/FileGroupFillDecrypt.cs — SpillOpen / FillChunks / LiveFill ordering against an AuthorizeGetDecryptPlan.
  • Services/Escrow/FordMmcsDecryptor.cs — PCSMMCS2 HKDF, AES-SIV Ford open, per-chunk keys, VerifyDigest.
  • Services/Escrow/PcsProtectionZone.cs (and neighbors) — zone-master unwrap of protectionInfo into IKM.
  • Protocol/CloudKitAssetProto.cs, BackupAssetContentsParser.cs, FileListSqliteParser.cs / DomainFileListParser.cs — asset metadata and file-list sides that feed signatures into authorizeGet, without substituting for IKM.

What this map is not

It is not a claim that Apple’s private MMCS will stay frozen, and it is not a guide to anyone else’s product. It is a reading of this codebase: how IKE turns a locked mbksync session into verified plaintext when the edge still holds the assets and the account holds the keys (zone masters, Octagon bottle or Recovery Key as required). For the chronological evidence behind each invariant, stay with Day 11; for the tooling that made early captures possible, see the companion lab note.
