How we got here, and what stayed true on the wire

Days 1–10 are dated notes written as we went. This entry is different: I put the story in order, and under each stretch I list the facts we still treat as solid—the ones that survived refactors because captures and live restores keep confirming them. Language first, then the evidence. Nothing here is a contract with Apple; private surfaces can move. It is what iCloudKit Extractor encodes today after months of checking.

March: ADP, EPB, Frida, GrandSlam

In late March 2026 we needed an ADP-protected iCloud backup and the commercial tools we used were not delivering it. With a colleague, under Forensis-Lab, I started from two things we already had: a jailbroken iPhone and a licensed copy of Elcomsoft Phone Breaker.

Watching EPB meant reverse-engineering a protected Windows binary. Themida-style packing (virtualization, API wrapping, anti-debug) was part of that. We used public research on unpacking Themida—including work from a student thesis on DBI-style recovery (write-then-execute, import rebuild, PE reconstruction)—and applied the same habits with x64dbg and session dumps. The point was never to ship a cracked product. It was to see which requests and responses mattered so we could reproduce them.

Early pain was GrandSlam. EPB was broken for the flows we needed; Elcomsoft fixed it the next month. I did not wait. iCloud.com gave idmsa web tokens (fine for browser Photos / trusted-device / SMS work, wrong for native mobile clients). On the phone, mobile GrandSlam and the first backup CloudKit names showed up: container com.apple.backup.ios, zone mbksync.

What we treat as solid from this stretch:

  • GrandSlam: lookup, then init at https://gsa.apple.com/grandslam/GsService2/ with A2k, Apple ID u, cpd, and ps: ["s2k", "s2k_fo"]. Complete sends u, c, M1, cpd only—an extra M2 field returns ec=-22410.
  • If the server omits iteration count i, we default to 20016.
  • CPD comes from Anisette (GrandSlamCpdBuilder): at least X-Apple-I-Client-Time, timezone/locale, X-Apple-I-MD, X-Apple-I-MD-M, X-Apple-I-MD-RINFO, X-Apple-I-MD-LU, X-Mme-Device-Id, plus bootstrap / svct=iCloud. AuthKitWin vs akd differ in capp and related fields.
  • RINFO constants we hard-code: Windows 84215040, iOS/akd 17106176. Soft reuse of MD is short (~3 minutes Client-Time refresh without reminting). Reminting mid-SRP breaks init/complete pairing (-22410 again).
  • After GSA: setup.icloud.com configurations/init and authenticate. Trusted-device secondary auth needs PET (com.apple.gs.idms.pet) for later escrow Basic auth.
  • Backup binding: container com.apple.backup.ios, bundle com.apple.backupd; zones _defaultZone, mbksync.

April: snapshots, then Lock

By 11 April we could list snapshots (S: after D:<sha>). EPB could talk to iOS 26 backups, but with ADP on we still got HTTP 403. That told us ADP is a server/crypto gate, not “old iOS.” We used their build as an oracle for how snapshot listing had been unblocked at all. backupProperties (UDID / Lockdown fields) stayed encrypted; we barely knew the field name yet.

Listing is not restoring. On 29 April the real exam was CloudKit Lock on mbksync before the large post-Lock catalog. Diary name “Prepare Restore Session” means that ordered climb; in code it is PrepareDownloadAsync / AcquireRestoreLockAsync—there is no separate public RPC called PrepareRestore in this tree. Frida on the phone plus a few malformed EPB request/response pairs (wrong for a clean download, useful as fossils) were how we reconstructed the state machine.

Important for the timeline: in April we could get Lock without yet decrypting backupProperties. The restore-host exam and the ADP KeySet are not the same step. The full path we ship today wants escrow / PCS KeySet before Lock and before authorizeGet; that KeySet is the October Octagon work, not something we already held on 29 April.

What we treat as solid from this stretch:

  • Record prefixes we rely on: D:<sha> (device), S: (snapshots), N: (post-Lock file-list / EN), KA: / MA: / LA: / NA: / JA: (asset families), :CN: / CN: (modern checksum entries), K: (keybag). Fixed name BackupAccount.
  • List path: zones → BackupAccount → D: → S:. Restore bootstrap we refuse to reorder: zones → Account → D: → S: → (optional mbs) → Lock → N:. Zone retrieve prefers record/retrieve, falls back to zone/retrieve.
  • Optional Mobile Backup stub: p32-mobilebackup.icloud.com / {partition}-mobilebackup.icloud.com, Accept application/vnd.com.apple.mbs+protobuf, header X-Apple-MBS-Protocol-Version: 2.2.
  • Lock record: name {deviceSha}:Lock (no leading hyphen on the sha), type Lock, zone mbksync, owner = device SHA (strip D:), duration 172800 seconds (48 h). Private modify-records (inner type 210 in our builder).
  • Failure string: Invalid lock id (MobileBackupServerExtension). Double-wrapping named protobuf fields historically produced Lockb9 vs Lockb7 with the same error.
  • Foreground Restore metadata rides in CAog-style auth tokens. For one analyzed account, HardwareId / plist SHA were stable across many sessions—not claimed for every account. mme-client-info varies; we merge it from live responses.
  • backupProperties: CloudKit field name on the snapshot; ciphertext shorter than ~16 bytes is ignored. Decrypt path: ShareProtection (zone and/or one-shot catalog unwrap) → CUWK label backupProperties → PCSFP-GCM, AAD type0 = field name. Without PCS KeySet on the session the field stays marked encrypted. Plaintext Lockdown.* feeds UI and prefers writing into Info.plist / Manifest.plist.
  • Zone-master cache artifacts: mbksync_zones_retrieve.bin, directory mbksync_zone_masters.

May–July: MMCS, IKM, Ford vs ChunkInfo

After about a month past Lock, on 24 May we were into MMCS: edge-content hosts, ranged GETs, blobs that are not one kind of thing. By then the phone and EPB were no longer daily crutches for the next problems. Coding agents and older public fragments about Octagon pointed at paths commercial “normal restore” never exposed. EPB stayed useful as an oracle for how they cached MMCS and reassembled chunks. Side-by-side through the summer we often held on the order of ~3000 more decrypted files than EPB—and still left a stubborn tail.

The same host and authorizeGet plan can carry Ford key material and data ChunkInfo. Mix them up and MAC checks fail while looking confident. On 16 June the missing piece for Ford was IKM: not the file-list EncryptionKey, but contents.protectionInfo unwrapped with the zone master. July was the caching war: forcing ranges and planting every lead-0x04 candidate sometimes opened a file and also poisoned the checksum21 .chunks/ map. The fix that stuck was to wait—Ford first when the blob really opens with IKM, data when it arrives, often after the gate.

What we treat as solid from this stretch:

  • authorizeGet URL: {contentHost}/{dsid}/authorizeGet. Hosts from {partition}-content.icloud.com or per-record ContentBaseUrl.
  • Request/response type: application/vnd.com.apple.me.ubchunk+protobuf. Header x-apple-mmcs-auth.
  • Auth header shape: {hex21_f2} {hex21_f17} {CAog…}—21-byte tokens (lead 01 or 04 + 20-byte digest). PreAuth scan pattern in tooling: 12 15 01… (f2) → 2a … CAog (f5) → 8a 01 15 01… (f17). Decoded CAog is expected to contain Foreground Restore and the signed-FG lead markers we check for.
  • Per-file entry: f1 = Assets.assetSignature verbatim (21 B, typically 0x04‖20B); f2 = CAog token string; f4 companion typically 0x01‖20B. Do not use the CK mmcs-auth part0 as f1. Batch header rebuild from entry[0]: hex(f1) + hex(f4) + ascii(f2).
  • Response: FileGroups—one group maps to one edge GET host (URL from template fields). Nested ChunkInfo: checksum (21 or 45 B), chunkEncryptionKey, ctLen, packOffset. Trailing file-checksum chunk references drive assembly order. Incomplete plans (missing URLs/signatures, range sum < declared size) are hard failures.
  • Edge GET query: content-byte-range={start}-{end}. Same object can expose Ford CT at offset 0 and data ChunkInfo at other ranges.
  • Asset name patterns include MA:udid:uuid:checksumB64:size and :CN:uuid:checksumB64.
  • IKM only from owned-record contents.protectionInfo unwrap with the zone master (16 or 32 B). File-list EncryptionKey poisons Ford opens.
  • Ford KDF (capture-checked): HKDF-SHA256(ikm=fileKey, salt="PCSMMCS2", info="", len=64)—not swapped salt/info. Output length 0x40.
  • Ford blob: lead(1) ‖ nonce(16) ‖ body, body = tag(16) ‖ ciphertext from offset 0x11. AES-SIV (RFC 5297), AD = [nonce, lead]. Per-chunk expansion: HKDF info signature-key, 0x60 bytes → k1/k2/k3.
  • Classic Auth Ford ctLen ∈ [0x12, 65536]. Larger bags (ctLen > 64 KiB, sanity cap 32 MiB) need ByteRange length ≥ ctLen. Empty-host Ford scan uses fixed window lengths (112…480) with a small scan cap (~4 KiB).
  • Ford gate descriptors often use a 45-byte checksum with lead bytes 0C 0F 01 04, distinct from 21-byte data checksums.
  • Data ChunkInfo: 21-byte checksum (MAC uses the trailing 20 bytes). Staging header length 0x28; little-endian u64 at hdr[0x20] is wire data length.
  • Cache under .chunks/ (or tmp CChunkCache), filenames = lowercase hex of the signature (42 hex chars for 21 B, 90 for 45 B gates). Ford plant: size == ctLen, typically lead 0x04, blob must open exactly with IKM—never plant Ford without IKM. Data CI21 may exceed 64 KiB.
  • LiveFill order: authorizeGet → FileGroups → ranged GET → Ford SpillOpen → FillChunks for storages that already have Ford keys → data ChunkDecrypt. Map keyed by Auth checksum21 accepts any data lead; Ford-prefix poison detection blocks data slices that open as Ford. Per-domain MmcsChunkAssemblySession shards avoid cross-contaminating FileGroup caches.

August: lead 0x04 vs 0xC4, then an iTunes-shaped tree

On 4 August the stubborn tail turned on a classifier bug. We had treated lead 0x04 as “Ford / decryptable.” Valid data chunks can start with 0xC4 and other non-0x04 values, including large bodies. That day unlocked a protocol-complete MMCS download for material that still lives on the edge. It did not finish ADP: zone masters and backupProperties still waited on Octagon in October. Orphans (names in inventory, no live MMCS asset) and non-Apple on-device crypto (e.g. some Mozilla model files in testing) sit outside this path.

By 28 August we could write an iTunes-shaped backup on disk so forensic tools see a familiar tree: hashed file paths, Manifest.db, sidecars.

What we treat as solid from this stretch:

  • Typical Ford CT at host offset 0 starts with 0x04. Strict gate-cache readers require compact[0] == 0x04.
  • Data chunks may start with 0xC4 (and other leads). Plant under hex(checksum21) regardless of lead. Gate45 prefix 0C0F0104 is descriptor metadata, not the data lead byte.
  • Device tree: {root}/{udid}/[{snapshotGuid}][{timestamp}]/ with clean Backup/ and work tmp/ (flist DBs, AUTH, keybag, mmcs cache, .chunks—removed after success).
  • Asset path: Backup/{fileID[0..2]}/{fileID}, fileID = SHA1 hex. Manifest rows use SHA1(domain + "-" + relativePath) in our writer.
  • Manifest.db from decrypted MA: candidates (SQLite magic after decrypt). Sidecars: Info.plist (XML), Status.plist, Manifest.plist (bplist); Manifest.plist prefers a copy of decrypted backupProperties.
  • Catalog evolution in tooling: modern S: → :CN: → EN:; classic S: → M: → files.

October: Octagon (PIN, then Recovery Key)

MMCS can fetch ciphertext forever; ADP still decides whether it decrypts. On 5 October we opened iCDP bottles with the trusted-device passcode. On 24 October, when that PIN path is unavailable, a known Recovery Key derives an Octagon peer locally and unwraps recoverable TLKShares. The public experimental note on 25 October is a release note, not another protocol day.

What we treat as solid from this stretch:

  • Escrowproxy get_records; Octagon-relevant labels com.apple.icdp.record.*. Recover against HSM is scarce (~10 attempts per record in our notes)—tooling treats recover as irreversible.
  • SRP secret is the device passcode, not legacy PCS dsid:dsid. Identity uses dsid with x = H(salt ‖ H(dsid ":" passcode)) (padded session-key variants exist in the escrow client). HTTP Basic(email, PET). Wrong M1 → credential errors (e.g. -6015); wrong recover header version can yield CLUBH -6122.
  • EscrowBottle plaintext exposes BottledPeerEntropy (~72 B). Cuttlefish container com.apple.security.keychain / cuttlefish coderouter: fetchViableBottles → AES-GCM OTBottle Contents → peer signing/encryption keys → KeySet.
  • Recovery Key KDF (RK is not sent as a password): HKDF-SHA384(ikm=UTF-8(RK), salt=UTF-8(altDSID), info, 56) with info Recovery Signing Private Key / Recovery Encryption Private Key. Deterministic P-384 (k = (entropy_be mod (q-1)) + 1). PeerId = RK- + Base64(SHA384(signing public key data)).
  • Cuttlefish fetchRecoverableTLKShares for that peer (protobuf string field 1 then 2). Prod path avoids a legacy RPC spelling that returned HTTP 500. Parses tlkshare / synckey records (names like tlkshare-…::RK-…).
  • Unwrap: ECIES on wrappedkey with the derived encryption private key → per-view TLKs. Wrong RK: shares may list, unwrap count is zero. OpenVault default views: Manatee, ProtectedCloudStorage, Passwords—feeds PCS seed for ADP zones and backupProperties.

What we still do not claim

  • That private CloudKit / MMCS / Cuttlefish stay frozen—experimental MIT software can break when Apple moves.
  • That every historical filename is recoverable (orphans, third-party encryption).
  • That Foreground HardwareId / plist SHA are universal (stable for one heavily analyzed account in our captures).
  • Forever-green emulated anisette; GSA needs a coherent ADI/akd-class stack (local Frida or a maintained remote Anisette server).

See also the 25 October release note: signed builds, Forensis-Lab attribution, no warranty that tomorrow’s wire matches this list.
