Themida, x64dbg MCP, and Frida on memcpy

Day 11 already mentioned Themida-style packing while we watched a commercial Windows tool. This note is the tooling story behind that sentence: how we approached the protector, how x64dbg driven through an MCP bridge shortened the work on virtualized and mutated code, which public research we used as a map, and how Frida on the same Windows process turned VC++ memcpy into a clean window on HTTPS request and response buffers.

The goal was never to redistribute a cracked binary. We needed the shape of Apple-facing traffic—headers, bodies, ordering—so iCloudKit Extractor could reproduce legitimate recoveries on accounts we control. Everything below is written at that level of detail: methodology and outcomes, not a unpack recipe.

Why Themida was on the critical path

Early in the project, commercial extractors were both an oracle and a wall. They could sometimes talk to surfaces we had not named yet; they could not always finish an ADP restore. Reading their Windows client meant reading a binary wrapped in a modern protector stack: packing, API wrapping, anti-debug noise, code virtualization, and instruction mutation.

Static disassembly alone was not enough. Large stretches of the interesting logic sat behind a virtual machine or behind mutated native code that only made sense after a runtime decode step. We needed a debugger that could stop at those decode moments, dump the resulting instructions, and keep session state across long lab nights.

A thesis as a map, not as a script

Before inventing our own path, we studied a master’s thesis PDF on modern software obfuscation and protection—DBI-oriented recovery, write-then-execute patterns, import rebuild, PE reconstruction, and the usual taxonomy of virtualization versus mutation. The document we used is Masters Thesis.pdf hosted alongside 67-6f-64/AntiOreans-CodeDevirtualizer; we did not run the accompanying code tool. That reading did not “solve Themida for us.” It gave us a shared vocabulary: which layers are expected to decrypt in memory, which traps are noise, and which artifacts (decoded regions, rebuilt imports, dump timing) are worth keeping when the goal is protocol understanding rather than a portable crack.

Combined with public write-ups on Themida-class packing, the thesis became a checklist we could argue about in the lab: are we looking at a virtualized handler, a mutated native block, or just anti-analysis theatre? Sorting that early saved weeks of chasing the wrong region.

x64dbg + MCP: accelerating decode work

Hands-on work happened in x64dbg. The accelerator was wiring the debugger to an MCP bridge so an AI coding assistant could drive the repetitive parts of a session: set and clear breakpoints around decode stubs, walk small windows of newly decrypted code, dump memory after a virtualized block finished, and annotate which mutated sequences had collapsed into readable instructions.

That mattered for two different protection styles we kept hitting:

  • Virtualized regions — interesting logic executed by a custom VM. Waiting for the handler to materialize a native window (or enough of a decoded buffer to reason about) was slow by hand. MCP-driven dumps after each interesting transition let us compare buffers across runs and keep only the stretches that touched network and crypto setup.
  • Mutated instructions — native code rewritten into equivalent but hostile forms. Here the win was speed of iteration: hit the decode site, capture the post-mutation bytes, ask for a structural reading, and decide whether the block was worth deeper attention or disposable noise.

None of that replaced human judgment. It compressed the loop between “the debugger stopped” and “we know whether this block teaches us an Apple RPC.” Session dumps from those nights still show up as breadcrumbs in the codebase (for example Ford / ChunkInfo notes that reference live x64dbg captures).

Frida on VC++ memcpy: reading HTTPS without fighting TLS

Decrypting protectors is only half the story. We still needed the plaintext of HTTPS requests and responses the commercial client was assembling. Breaking TLS on the wire was the wrong fight: pinning, custom stacks, and Themida wrapping made MITM noisy and fragile.

Instead we attached Frida to the Windows process and hooked the Visual C++ runtime memcpy (and close relatives in the same CRT family). Large HTTP bodies, plist blobs, and protobuf payloads almost always pass through a memory copy before send or after receive. Filtering those copies by size and by recognizable prefixes (POST, HTTP/1, XML/plist headers, CloudKit-ish binary markers) gave us request/response pairs at the moment they existed as ordinary buffers—after application crypto for Apple payloads, before or after the TLS record layer depending on where the copy sat.

That technique is blunt and noisy; it also works when certificate pinning would defeat a proxy. Paired with the x64dbg work, it let us label which decoded regions were worth studying: a mutated block that never touched a memcpy of a network buffer was usually less urgent than one that did.

Separately, Frida on a jailbroken iPhone remained the preferred path for Anisette / akd identity (see the README and Day 3). The VC++ memcpy hooks described here are the Windows-side companion for studying the commercial client, not a replacement for on-device OTP minting.

What we took into iCloudKit Extractor

The durable output was not an unpacked EXE. It was a pile of labeled captures and a short list of invariants that later survived refactoring: GrandSlam CPD shape, Lock ordering, authorizeGet / FileGroups, Ford versus ChunkInfo, IKM / PCSMMCS2, Octagon bottles and Recovery Key TLKShares. Day 11 lists those wire facts. This note is how we got close enough to the protected client to learn them without pretending the protector did not exist.

Lab takeaways we still use:

  • Treat Themida-class protection as layered (pack / wrap / virtualize / mutate); name the layer before spending a night on it.
  • Use public obfuscation research (including thesis-grade DBI maps) as a checklist, not as a push-button unpacker.
  • Drive x64dbg through MCP for decode dumps and mutation windows; keep humans on protocol judgment.
  • Prefer Frida on VC++ memcpy (Windows) for HTTPS buffer visibility when TLS MITM is the wrong tool; keep Frida-on-akd for Anisette.
  • Ship only what is needed for recovery on accounts you control—never a cracked third-party binary.
